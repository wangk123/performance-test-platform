# Agent 化性能测试平台方案设计与对比

> 状态：想法评审稿  
> 日期：2026-07-24  
> 目的：完善设计并支持团队评审，不在本文中选择最终方案。

## 1. 文档目的

本文讨论在性能分析数据链完整的前提下，平台如何支持 AI 辅助性能分析与优化，并对比两种产品路线：

1. 平台集成 AI 助手，由平台承担多轮分析和交互。
2. 平台作为完整工具集，通过 REST、MCP 和 SKILL 供 Claude Code 等外部 Agent 使用。

本文重点回答：

- 两种方案需要共享哪些平台能力。
- 平台如何形成可被 Agent 完整驱动的工具面。
- 两种方案在相同数据条件下的效果、成本和长期维护差异。
- 如何分阶段建设共同底座，并为后续选型保留空间。

本文不决定最终采用哪种方案，也不替代后续实施级 OpenSpec。

## 2. 背景与现状

平台已经具备项目、脚本、计划、场景、压测执行、聚合指标、秒级指标、失败样本、Prometheus 监控、报告和造数等能力，大部分主流程已通过 REST API 提供。

平台已有 LLM Provider、Model、协议适配、统一调用和调用记录，但当前 LLM 能力主要是单次调用底座，不包含：

- Tool Calling。
- 多轮会话。
- 上下文压缩。
- Agent 运行状态和恢复。
- 工具规划和停止策略。
- Agent 质量评测。

当前 API 主要服务前端 UI，尚未形成统一的 Agent 工具契约；身份认证、机器凭据、细粒度授权、审计和 OpenAPI 也需要进一步完善。

## 3. 共同前提与设计边界

### 3.1 比较前提

两种方案都以完整性能数据链已经建设完成为前提。以下能力属于共同成本，不用于证明某个方案成本更高或效果更好：

- 压测配置和执行上下文。
- 聚合指标与时序指标。
- 失败样本和执行日志。
- 服务器与 JVM 监控。
- Trace、应用日志、慢 SQL、执行计划和 Profiling。
- 数据可用性、采样范围、截断和缺失说明。
- 确定性分析和跨执行对比。
- 补充取证和优化验证。
- 权限、审计、脱敏、幂等和风险控制。

两种方案的差异主要在于：Agent 运行在哪里，以及谁承担会话、上下文、交互、推理和代码优化能力。

### 3.2 目标用户

目标用户是具备性能工程能力的资深开发和测试人员。外部 Agent、MCP 和 SKILL 的安装与使用门槛不作为核心阻碍。

### 3.3 能力开放范围

目标是让平台全部业务能力原则上都可通过策略向 Agent 开放，包括查询数据、管理测试资产、创建和执行压测、补充取证以及验证优化结果。

能力不采用全局硬编码的绝对禁止清单，而采用基于用户、角色、项目、环境和工具的策略控制：

- 普通角色可使用项目内的常规查询和压测能力。
- 高级角色可按授权使用服务器数据、SQL、CLI、脚本、监控部署和系统配置等扩展能力。
- 管理角色可管理平台级用户、角色、凭据和配置。
- 高风险操作是否需要确认，可由角色和环境策略决定。

CLI、脚本和 SQL 的具体执行方式不是本次方案对比的重点，后续单独设计。

## 4. 共同目标架构

两种方案应建立同一个 Agent-ready Platform Core，避免为平台内 Agent 和外部 Agent 分别建设数据与执行逻辑。

```text
┌───────────────────────┐    ┌────────────────────────┐
│ 方案 1：平台内 Agent  │    │ 方案 2：外部 Agent     │
│ UI / Agent Runtime    │    │ Claude Code + SKILL    │
└───────────┬───────────┘    └────────────┬───────────┘
            │                             │
            │                  ┌──────────▼──────────┐
            │                  │ MCP / REST Adapter │
            │                  └──────────┬──────────┘
            └─────────────────────────────┤
                                          ▼
                         ┌────────────────────────────┐
                         │ Agent-ready Platform Facade│
                         └─────────────┬──────────────┘
                                       ▼
     ┌────────────────────────────────────────────────────────┐
     │ 资产 | 执行 | 数据 | 确定性分析 | 取证 | 验证 | 策略 │
     └────────────────────────────────────────────────────────┘
                                       ▼
     ┌────────────────────────────────────────────────────────┐
     │ DB | 指标 | SQLite 样本 | Prometheus | 日志 | APM     │
     └────────────────────────────────────────────────────────┘
```

### 4.1 Agent-ready Platform Facade

Facade 是 UI、平台内 Agent、REST 和 MCP 的统一业务入口，负责：

- 聚合跨模块业务能力。
- 校验身份、项目权限和环境范围。
- 执行风险策略和必要确认。
- 统一幂等、审计和错误语义。
- 限制查询范围和响应大小。
- 隔离底层数据库、文件、监控和执行引擎差异。

任何 Agent 均不能绕过 Facade 直接访问 Repository、执行文件或监控存储。

### 4.2 确定性分析层

平台负责可重复计算的事实，包括：

- 响应时间、吞吐量和错误率趋势。
- 异常时间窗口和性能拐点。
- 请求或接口贡献度。
- 错误类型聚类与分布。
- CPU、内存、GC、线程和连接池饱和。
- 压测指标与资源指标的时间相关性。
- 基线与候选执行的可比性和差异。

该层输出事实、算法版本、输入范围、完整度和证据定位，不输出依赖 LLM 推理的根因结论。

### 4.3 策略与治理层

治理能力横跨所有工具：

- 用户、角色、项目和环境授权。
- 工具级权限和作用域。
- 请求审计和执行审计。
- 并发、超时、配额和速率限制。
- 敏感字段脱敏和数据外发策略。
- 高风险操作的预检、确认或角色豁免。
- 异步任务状态与取消。

## 5. 完整数据链设计

### 5.1 数据域

完整数据链至少包括：

- 测试资产：脚本版本、参数、数据文件、计划、场景和负载模型。
- 执行上下文：执行时间、环境、节点、脚本版本、负载配置和目标版本。
- 压测结果：聚合指标、时序指标、分位数、吞吐量和错误率。
- 失败证据：失败摘要、样本、请求、响应和异常类型。
- 资源监控：主机、容器、JVM、中间件和数据库指标。
- 深度证据：Trace、应用日志、慢 SQL、执行计划和 Profiling。
- 历史数据：同场景基线、趋势、版本和环境变化。
- 验证数据：优化前后执行、可比性、主指标和护栏指标。

### 5.2 数据访问原则

Agent 使用数据时遵循：

1. 先查询数据可用性。
2. 再读取摘要和确定性事实。
3. 根据假设按时间、对象或证据类型下钻。
4. 需要补充数据时提出取证动作。
5. 修改完成后使用相同语义执行验证。

工具必须显式返回：

- 数据是否存在。
- 时间覆盖范围。
- 采样和聚合方式。
- 是否被截断。
- 是否仍可回溯原始来源。
- 数据缺失或删除原因。

禁止用其他时间段、其他实例或其他数据源静默替代缺失数据。

### 5.3 海量数据策略

原始海量数据保留在来源系统中。平台向 Agent 提供有界摘要、查询游标和来源定位：

- 指标按时间窗口和粒度查询。
- 日志、Trace 和样本按过滤条件分页。
- Profiling 先返回摘要和热点，再下钻具体调用路径。
- 每次响应设置条数、字节和耗时预算。
- 超出预算时返回截断状态和下一步查询建议。

无论 Agent 位于平台内部还是外部，都必须采用相同策略；外部 MCP 不是额外的数据旁路。

## 6. 平台能力与工具面

### 6.1 上下文和资产工具

- 查询项目、环境和可用能力。
- 查询和管理脚本、计划、场景及版本。
- 校验测试资产引用和执行前配置。
- 查询历史执行和可比较基线。

### 6.2 压测执行工具

- 执行预检和影响评估。
- 创建、启动、停止和取消执行。
- 查询队列、节点、实时进度和执行日志。
- 查询执行终态和产物可用性。

写操作支持幂等键。高风险操作默认可使用“预检 + 一次性确认令牌”，但策略可按角色和测试环境调整。

### 6.3 数据和证据工具

- 获取数据可用性。
- 查询执行摘要。
- 查询聚合和时序指标。
- 查询失败分布和失败样本。
- 查询服务器、JVM、中间件和数据库指标。
- 查询 Trace、日志、慢 SQL、执行计划和 Profiling。
- 获取证据摘要和原始来源定位。

### 6.4 确定性分析工具

- 检测异常区间和性能拐点。
- 分析错误聚类和请求贡献度。
- 识别资源饱和与时间相关性。
- 比较多个执行或版本。
- 评估执行间可比性和结果波动。

### 6.5 补充取证和验证工具

- 生成取证动作预检。
- 启动补充压测或数据采集。
- 查询取证进度和新增数据。
- 登记代码或配置变更引用。
- 发起优化验证。
- 查询验证结果和护栏指标。

### 6.6 扩展能力

目标服务器数据、SQL、CLI、脚本、监控部署和平台配置可作为策略控制的扩展工具。本文仅要求它们复用统一身份、授权、审计和风险策略，不规定具体执行器。

## 7. REST、MCP 与 SKILL

### 7.1 共享语义、不同粒度

REST 和 MCP 都调用共享 Facade，但不要求一一映射：

- REST 面向程序和自动化，保持资源型接口。
- MCP 面向 Agent，采用任务型工具并减少工具数量。
- MCP 工具可以编排多个只读 Facade 查询，但不能复制业务规则。
- 写操作必须保持单一明确语义，避免隐式执行多个高风险动作。

### 7.2 MCP 响应约定

MCP 和面向 Agent 的 REST 响应统一包含：

- `requestId`
- `schemaVersion`
- `data` 或结构化错误
- `warnings`
- `truncated`
- `nextCursor`
- 数据范围与完整度说明

错误使用稳定代码区分认证失败、权限不足、资源不存在、数据源不可用、查询过大、超时、限流、幂等冲突和执行冲突。

### 7.3 工具发现和上下文控制

不应将所有工具 schema 一次性注入 Agent 上下文。可按项目能力、用户角色和当前任务动态提供工具：

- 初始只暴露导航和能力发现工具。
- 进入压测设计时加载资产与执行工具。
- 进入诊断时加载数据、证据和分析工具。
- 进入验证时加载变更登记和验证工具。

### 7.4 模块化 Skill Pack

方案 2 提供以 Claude Code 为首期验收对象的 Skill Pack：

- 平台导航：发现项目、环境、数据和可用工具。
- 压测设计：创建或调整脚本、计划和场景。
- 执行观察：预检、启动、监控和停止执行。
- 性能诊断：从数据可用性开始，基于证据逐层调查。
- 补充取证：识别数据缺口并发起补充采集。
- 优化验证：登记变更并比较基线与候选执行。

SKILL 负责指导操作顺序、证据规范和停止条件；权限、数据范围和执行风险仍由平台强制控制。

## 8. 端到端工作流

```text
选择项目和目标环境
  → 查询可用测试资产与数据能力
  → 创建或选择压测场景
  → 执行预检并按策略确认
  → 启动压测并观察实时状态
  → 查询数据可用性和确定性事实
  → 按需下钻指标、样本、监控和深度证据
  → 数据不足时发起补充取证
  → Agent 与用户多轮讨论根因假设和优化方案
  → 开发人员或外部 Agent 修改代码或配置
  → 登记变更并发起候选压测
  → 平台比较基线和候选执行
  → 输出改善、退化或无法判定
```

该流程在两种方案中的领域步骤相同。差异仅在多轮调查和方案决策发生在平台内 Agent，还是 Claude Code 等外部 Agent。

## 9. 方案 1：平台集成 AI 助手

### 9.1 架构

平台新增 Agent Runtime 和诊断工作区：

```text
诊断 UI
  → Agent Runtime
      → LLM Gateway
      → Tool Registry
      → Session / Context / Budget / Approval
  → Agent-ready Platform Facade
```

现有 LLM Gateway 可继续提供模型配置、协议适配和调用记录，但不能替代 Agent Runtime。

### 9.2 平台新增职责

- 多轮会话和消息持久化。
- Tool Calling 和工具结果管理。
- 上下文选择、裁剪、压缩和恢复。
- Agent Run、Step、暂停、取消和重试。
- Token、费用、时间和步骤预算。
- 工具规划、停止条件和数据不足退出。
- 用户审批和诊断工作区交互。
- Agent 运行回放和质量评测。
- 模型差异适配和持续调优。

### 9.3 优点

- 用户无需离开平台。
- 数据查询延迟低，领域上下文容易自动注入。
- 会话、证据、决策和结果集中保存。
- 权限、模型、费用和数据外发可统一治理。
- 多人共享和过程审计更自然。
- 不依赖用户安装外部 Agent。

### 9.4 缺点

- 需要建设并长期维护完整 Agent harness。
- 上下文管理、会话压缩和流程控制复杂。
- 很难达到成熟编码 Agent 的本地代码、CLI、Git 和测试体验。
- 平台承担模型并发、成本、稳定性和兼容性。
- 调查自由度受到平台产品交互限制。
- 容易分散对数据链和确定性分析的投入。

## 10. 方案 2：平台工具集 + 外部 Agent

### 10.1 架构

平台不建设通用 Agent Runtime，新增标准 MCP 接入和 Skill Pack：

```text
Claude Code
  ├── 用户与多轮会话
  ├── 本地代码 / CLI / Git / 测试
  ├── 平台 Skill Pack
  └── MCP Client
        → Platform MCP Server
            → Agent-ready Platform Facade
```

平台定位为可被 Agent 完整驱动的性能工程能力宿主。

### 10.2 平台新增职责

- Streamable HTTP MCP Server。
- 面向 Agent 的工具设计和动态注册。
- 机器身份、授权和凭据管理。
- MCP 结果分页、截断、重试和错误映射。
- Claude Code Skill Pack。
- MCP、REST 和 Skill 版本兼容。
- 真实 Claude Code 工作流验收。

### 10.3 优点

- 复用成熟 harness 的多轮交互和上下文管理。
- 性能调查与本地源码分析、修改、CLI、Git 和测试处于同一会话。
- 用户可组合平台、代码仓库、文档、联网查询和其他 MCP。
- 平台集中投入领域数据、分析和压测能力。
- 无需承担通用 Agent Runtime 和诊断聊天 UI。
- 可直接受益于外部 Agent 产品升级。

### 10.4 缺点

- 需要安装 Skill、配置凭据并处理客户端兼容。
- 数据可能发送到外部模型，需要数据策略和脱敏支持。
- 外部会话不天然属于平台，多人共享和完整回放较弱。
- 分析效果受模型、Skill 遵循程度和用户操作影响。
- MCP 工具粒度和返回质量直接影响使用体验。
- 对 Claude Code 的行为和版本存在外部依赖。

## 11. 方案对比

以下比较均基于两种方案拥有相同的完整数据链和确定性分析能力。

### 11.1 分析能力上限

两种方案获得相同数据和事实时，信息上限接近。Agent 的最终质量仍受模型、Prompt、工具设计和用户判断影响。

方案 1 更容易固化统一流程并持续评测；方案 2 更适合自由调查和组合外部信息。

### 11.2 多轮调查体验

方案 1 需要自行实现会话、上下文和交互体验。方案 2 直接使用 Claude Code 的成熟能力，在长流程、临时追问、跨工具调查和方案讨论方面更有优势。

### 11.3 代码优化闭环

方案 1 的 Agent 运行在平台侧，与开发者本地仓库、Git 和测试环境存在天然距离。

方案 2 的分析与代码修改发生在同一个工作区，能够直接阅读源码、执行命令、修改代码和运行测试，闭环更短。

### 11.4 治理、审计和复现

方案 1 的会话和推理过程由平台管理，更容易集中审计、共享和回放。

方案 2 的平台工具调用可以完整审计，但外部 Agent 的全部上下文、联网信息和本地操作不一定能回传平台，因此端到端复现能力较弱。

### 11.5 用户门槛

方案 1 对普通平台用户更友好。方案 2 要求用户具备 Claude Code、MCP 和性能工程使用能力。

本设计的目标用户是专业开发和测试人员，因此方案 2 的工具门槛不是核心评价因素，但仍存在配置和维护成本。

### 11.6 外部依赖

方案 1 主要依赖模型 API，产品行为由平台控制。

方案 2 依赖 Claude Code 的 MCP、SKILL、权限和会话行为，需要兼容性测试和版本跟踪。

### 11.7 数据安全

方案 1 更容易限制数据不离开平台控制的模型链路。

方案 2 需要明确哪些数据可发送到外部 Agent 和模型，并在工具输出前实施权限校验、脱敏和响应预算。

## 12. 实现成本

### 12.1 共同成本

完整数据链、确定性分析、共享 Facade、REST、权限、审计、取证和验证属于共同基础，整体成本高，但不计入两个方案的增量差异。

### 12.2 方案 1 增量成本

增量实现成本高，主要来自：

- Agent Runtime。
- 会话与上下文管理。
- 暂停恢复和异步状态机。
- 预算、停止和故障治理。
- 诊断 UI 和用户审批体验。
- Agent Eval 和持续模型调优。
- 与源码、CLI 和开发工作流的后续集成。

长期维护成本同样较高，因为模型协议、上下文策略、工具行为和交互体验都需要持续演进。

### 12.3 方案 2 增量成本

增量实现成本中等，主要来自：

- MCP Server 和工具契约。
- 机器身份与授权。
- 工具分页、截断、幂等和错误处理。
- Skill Pack。
- Claude Code 兼容性与端到端验收。
- 工具与 Skill 的版本维护。

由于目标是开放平台大部分业务能力，MCP 工具设计和治理并非低成本；但不需要建设通用 Agent Runtime、会话系统和诊断聊天 UI。

## 13. 与 Claude Code 等成熟产品的差距

若采用方案 1，平台与 Claude Code 的主要差距不在 MCP，而在完整 harness：

- 长会话上下文管理。
- 自动压缩和信息保留。
- 稳定的工具调用循环。
- 本地文件、CLI、Git 和测试集成。
- 修改、验证和失败恢复。
- 权限体验和用户确认。
- 模型适配与持续优化。

这些能力具有较高工程复杂度和长期产品投入。平台可以在性能领域数据、确定性分析、取证和验证方面形成优势，但短期内难以复制成熟编码 Agent 的通用能力。

若采用方案 2，平台不需要缩小这部分差距，而是通过 MCP 和 SKILL 将领域优势提供给成熟 harness。

## 14. 错误处理与可靠性

### 14.1 数据源失败

单个监控、日志或 Trace 数据源失败时，其他可用数据仍可查询。响应必须明确缺失来源和影响，不能静默降级。

### 14.2 查询过大

超出条数、字节或耗时预算时返回截断状态和游标，不直接失败或一次性返回全部数据。

### 14.3 写操作重试

创建和执行类操作使用客户端幂等键。网络重试必须返回原请求结果，不能重复启动压测。

### 14.4 异步执行

压测、取证和验证返回稳定任务 ID。Agent 通过状态工具查询，不依赖长时间同步连接。

### 14.5 权限与资源隐藏

无权限资源与不存在资源应避免泄露敏感差异。审计中保留真实拒绝原因，外部响应使用稳定错误语义。

### 14.6 版本兼容

REST、MCP、SKILL、领域 DTO 和确定性算法分别记录版本。破坏性变更必须提供迁移窗口或新版本工具。

## 15. 质量验证

### 15.1 共同底座验证

- 固定数据集验证数据可用性、采样、截断和缺失语义。
- 确定性算法使用黄金样本验证可重复性。
- Facade 验证项目权限、角色策略、审计和幂等。
- 海量数据验证分页、响应预算和取消。
- 补充取证与验证流程执行端到端测试。

### 15.2 方案 1 专项验证

- 多轮会话和上下文压缩不丢失关键证据。
- Agent 不绕过工具和权限。
- 数据不足时能够停止并说明缺口。
- 使用历史 Case 评估证据忠实度、工具效率、成本和耗时。
- 故障、取消和恢复后状态一致。

### 15.3 方案 2 专项验证

- 使用 Claude Code 完成真实 MCP 初始化和工具发现。
- 验证 Skill 能指导 Agent 从数据可用性开始调查。
- 验证分页、截断、重试、幂等和结构化错误。
- 验证压测创建、执行、分析、补证和优化验证的完整流程。
- 验证 Claude Code 版本升级后的兼容性。
- 验证工具调用审计能够重建平台侧操作轨迹。

## 16. 分阶段路线

本节描述从平台当前状态到目标架构的建设顺序；第 11、12 节的方案比较仍以这些共同阶段已经完成为前提。

### 阶段一：能力盘点与统一契约

- 盘点 UI、REST 和领域 Service 的完整能力。
- 建立 Agent-ready Platform Facade。
- 统一身份、项目授权、错误、幂等和审计。
- 形成 REST/OpenAPI 与 MCP 共享的领域 DTO。

### 阶段二：完整数据链

- 统一执行上下文和数据可用性。
- 接入平台原生指标、样本和监控。
- 逐步接入 Trace、日志、慢 SQL、执行计划和 Profiling。
- 建立有界查询、来源定位和数据保留语义。

### 阶段三：确定性分析与验证

- 建立异常、趋势、拐点、错误、饱和和对比分析。
- 建立补充取证流程。
- 建立基线与候选执行验证。
- 形成固定数据集和质量基线。

### 阶段四 A：平台内 Agent 路线

- 建立最小 Agent Runtime。
- 建立会话、Run/Step、工具循环和预算。
- 建立诊断工作区和审批交互。
- 建立 Agent Eval 和运行回放。
- 逐步增强上下文压缩、恢复和代码工作区集成。

### 阶段四 B：外部 Agent 路线

- 建立 Streamable HTTP MCP Server。
- 暴露导航、数据、分析、压测和验证工具。
- 建立机器身份、授权和审计。
- 发布 Claude Code Skill Pack。
- 使用真实项目完成端到端验收。
- 后续扩展 Cursor 和其他标准 MCP Client。

阶段四 A 和阶段四 B 可以在完成共同底座后独立评估，不要求当前文档作出选择。

## 17. 主要风险

- 完整数据链建设不足，导致两种 Agent 都只能输出表面结论。
- 将现有 REST 机械映射为大量 MCP 工具，造成上下文膨胀和工具误用。
- Facade 缺失，导致 UI、REST、MCP 和 Agent 出现多套业务规则。
- 数据可用性和截断语义不明确，导致 Agent 把部分数据视为全量。
- 写操作缺少幂等和环境范围控制，导致重复或错误执行。
- 方案 1 低估 Agent harness 的长期维护成本。
- 方案 2 低估 MCP 工具设计、Skill 维护和客户端兼容成本。
- 过早选择方案，导致共同数据与分析能力建设被交互形态绑架。

## 18. 评审重点

本次评审建议重点讨论：

1. “完整数据链”的范围是否足以支持代码级性能分析。
2. 共享 Facade 是否应成为所有 UI、REST、MCP 和 Agent 的强制边界。
3. 平台业务能力的开放范围与角色策略是否合理。
4. 两种方案的增量成本判断是否符合团队能力和长期投入预期。
5. 平台是否需要保存外部 Agent 的调查过程，还是只审计平台工具调用。
6. Claude Code 是否足以作为方案 2 的首期唯一验收客户端。
7. 共同底座完成到什么程度后，才具备选择方案的有效依据。

## 19. 当前结论

- 两种方案都可行。
- 数据链、确定性分析、共享 Facade 和执行验证是共同且优先的核心能力。
- 方案 1 的主要价值是集中体验、治理和复现，主要代价是自建成熟 Agent harness。
- 方案 2 的主要价值是复用成熟交互和编码闭环，主要代价是外部依赖、数据策略和工具契约治理。
- 在完整数据条件下，两种方案的诊断信息上限接近，但多轮交互、代码优化、平台治理和长期工程成本存在明显差异。
- 本文保持中立，不作最终路线选择。
